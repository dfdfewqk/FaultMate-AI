# FaultMate AI — P4 ML 개발 조건 (Antigravity 담당)

## 현재 상태

**P6 구현 이후: CSV 특성 검증·그룹 분리 학습·평가·검증 모델만 추론하는 코드가 구현되었습니다. 실제 측정 데이터 변환·학습·정답 검증은 미완료이며 현재 ML 미연결입니다.** P2의 7개 교육용 사례는 학습 라벨이 아니며 모델 성능 측정에 사용하면 안 됨. MicroLoss의 미세정지 ML도 전환하지 말 것.

## 우선순위

1. 예측 대상을 한 문장으로 정의한다. 예: "동일 유형 구동모터의 진동 기록으로 베어링 실험 고장/정상 상태를 구분". 컨베이어 전체 고장 원인 진단과 혼동하면 안 된다.
2. 데이터셋의 출처, 라이선스, 설비 모델, 관측값 단위, 센서 표본율, 라벨 취득 방식, 대상 고장 유형을 문서화한다.
3. 동일 원시 시험·장비의 연속 구간이 train/test에 동시에 섞이지 않게 **설비/시험 단위 분할**한다. 시간순 배치가 의미 있는 데이터에는 시계열 누출도 검사한다.
4. train-only 전처리/특징 추출 → 검증 세트에서 기준 설정 → 독립 시험 세트에서 재현 가능한 평가. 클래스별 precision/recall, confusion matrix, 고장 유형별 오탐·미탐과 미지/결측 처리 포함.
5. 모델 버전, 데이터셋 해시, 학습 코드 버전, 평가 기준을 기록. 실제 운용 대상 설비와 다른 실험 데이터이면 일반화 한계를 화면에 표시.
6. 통합은 `ml.status=unavailable|validated|unsupported_input|error`처럼 **명시적인 상태**로 구현. 미학습·미검증 상태에서 임의 확률 또는 가짜 예측 수치를 그리지 말 것.
7. 규칙 기반 점검 안내와 ML 예측을 별도 카드로 보여준다. 모델 점수는 고장 확정이나 작업 허가가 아니며 `safety_hold`에서 자동 점검 제안으로 우회 금지.

## 데이터 레코드 제안 (실제 데이터 확보 전 샘플 규격일 뿐)

```
asset_id,trial_id,timestamp_utc,sensor_id,value,unit,fault_label,label_provenance
```

`fault_label`은 실제 자료의 의미와 1:1로 매핑된 경우만 허용. `label_provenance`에 시험 조건·검사 기록 등의 정답 획득 근거 포함. 실제 진단용 센서 입력이 없으면 ML 추론을 제공하지 않는 게 올바름.

## 평가 통과 기준

분리된 시험 세트 및 안전한 실패 동작 확인 전에는 성능 수치 발표 금지. 숫자 목표를 미리 정했다고 높은 정확도가 보장되는 건 아님. 충분한 정답 데이터가 없으면 **ML은 제외하고 근거 기반 에이전트부터 완성**해도 됨.
